# Security Audit — 2026-08-24 (1.5.3 P(-1) sweep)

Scope: all 9 surviving modules (`error`, `util`, `udev`, `drm` + the deferred
Linux-eccentric group `journald`, `netns`, `bootloader`, `update`, `fuse`),
plus the local/CI quality gates. Toolchain: cyrius 6.5.35.

Method follows [CLAUDE.md § Security Hardening](../../CLAUDE.md): input
validation, buffer safety, syscall review, pointer validation, command
injection, path traversal, CVE landscape.

**Result: 1 HIGH, 2 MEDIUM, 4 LOW. All 7 closed in 1.5.3.**

Prior round: [`2026-06-01-audit.md`](2026-06-01-audit.md) (1.3.0).

## F-5 (HIGH) — `fuse_parse_proc_mounts` 1-byte heap overflow

`src/fuse.cyr` allocated exactly 8192 bytes, read up to 8192 bytes into it,
then NUL-terminated at `buf + total_read`. On a read that fills the buffer,
`total_read == 8192` and `store8(buf + 8192, 0)` writes one byte past the
allocation.

**Reachability.** `/proc/mounts` crosses 8192 bytes at roughly 90 mount
entries — routine on container hosts, Kubernetes nodes, and snap-heavy
desktops. The audit host carries 28 mounts / 2530 bytes, which is why the
existing test suite never tripped it.

**Confirmation.** Proven, not inferred: a heap-canary harness reproducing the
exact allocate/fill/terminate shape corrupts **1 byte** of the following
allocation under `alloc(8192)` and **0 bytes** under `alloc(8192 + 1)`.

**Why it survived.** This is the third instance of one bug class. It was found
and fixed twice before — `update_check` (F-11, 1.3.0, which carries an inline
comment describing precisely this hazard) and `agnodrm_read_fd_to_str`
(1.3.1, which allocates `cap + 1` for the same reason). `fuse.cyr` was missed
by both sweeps.

**Fix.** `alloc(8192 + 1)`, matching the canonical `cap + 1` helper.

**Residual.** `/proc/mounts` beyond 8192 bytes is still silently truncated;
the parse then yields a partial mount list rather than an error. Pre-existing
behaviour, unchanged here, and noted in SECURITY-NOTES.

## F-1 (MEDIUM) — kernel cmdline denylist gaps

`bootloader_validate_kernel_cmdline` matches each space-delimited token
exactly against a 21-entry denylist. Gaps found:

- **`rdinit=` absent entirely.** It overrides the *initramfs* init to an
  arbitrary binary — the same escape `init=` provides. Nothing matched it.
- **`init=` enumerated three shells** (`/bin/sh`, `/bin/bash`, `/bin/dash`).
  `zsh`, `ksh`, `csh`, `tcsh`, `ash`, `busybox`, and `sulogin` walked through.
- **No rescue/emergency targets** — `systemd.unit=rescue.target`,
  `systemd.unit=emergency.target`, `rescue`, `rd.rescue`.
- **No CPU-mitigation or KASLR downgrades** — `mitigations=off`, `nopti`,
  `pti=off`, `nospectre_v1/v2`, `nosmep`, `nosmap`, `nokaslr`, `kaslr=off`,
  `noexec=off`.
- **No `security=none` / `selinux=permissive`.**

**Fix.** 27 entries added; `rdinit=` matched by *prefix* rather than
enumerated (it never appears in an ordinary cmdline, so any value is
suspect). Guarded by a length + first-byte test to keep it off the per-token
cost.

**Residual — read this before relying on the function.** It remains a
**denylist**. `Ok(0)` means "nothing listed matched", not "safe": an unlisted
interpreter, an equivalent spelling, or a novel kernel parameter still passes.
The SysV single-user tokens `S` and `1` were deliberately *not* added — a bare
`1` is too generic to denylist without false positives. The doc comment and
SECURITY-NOTES now state this limit explicitly; an allowlist-based API is
roadmap V2.0.

## F-6 (MEDIUM) — netns firewall port unvalidated

`netns_fw_rule_new` accepts any i64 port. Two sites in
`netns_render_nftables_ruleset` rendered it with `fmt_int_buf` into
`alloc(8)`, then wrote a NUL at `pbuf + plen`. `fmt_int_buf` of an i64 needs
up to 20 digits plus sign, so any port of 8+ digits wrote past the buffer.
Only `port > 0` was checked; there was no upper bound.

**Fix.** Bound to the real TCP/UDP range (`port > 0 && port <= 65535`) and
size the scratch buffer at 24 bytes, matching the `[24]` i64-scratch
convention already used in `error.cyr` and `update.cyr`. Out-of-range ports
are now skipped rather than emitted — an nft rule with a 9-digit port cannot
load anyway, so emitting one would fail the whole ruleset.

## F-7 (LOW) — netns `prefix_len` lower bound

`netns_validate_config` rejected `plen == 0` and `plen > 32`. A negative value
passed both, and `netns_create_agent_netns` formats it into an `alloc(4)`
scratch — a large negative needs far more than 3 characters. Fixed to `< 1`.

## F-3 (LOW) — `drm_list_devices` trusted `d_reclen`

The getdents64 walk read `d_reclen` and advanced `pos` by it with no
validation. `reclen == 0` spins the loop forever; a `reclen` past `nread`
walks `name_ptr` into uninitialised heap, and `strlen(name_ptr)` could run off
the 4096-byte buffer entirely.

Unreachable in practice — `/dev/dri` is devtmpfs and the kernel emits
well-formed dirents — so this is defence-in-depth. Fixed with a
`reclen >= 20` / `pos + reclen <= nread` guard plus a bounded NUL scan that
never hands `d_name` to `strlen`.

## F-4 (LOW) — `drm_get_driver_version` negative length

The DRM version ioctl's `name_len` / `date_len` / `desc_len` are
`__kernel_size_t` (u64). Read back as i64, anything ≥ 2^63 reads negative, and
the `> 4096` cap does not catch that; `alloc(len + 1)` would then receive a
bogus size. Clamped low as well as high.

## F-2 (LOW) — `bootloader_is_dangerous_token` is misleading API

Public, and called by **nothing in production** — only the benchmark suite.
Worse, its semantics diverge from the validator beside it: it does a
case-insensitive *substring* search, while `bootloader_validate_kernel_cmdline`
does *exact per-token* matching. A consumer reaching for the obvious-looking
helper gets different (looser) behaviour than the library's own validator.

**Not removed** — it is in the frozen 1.0 API surface, so removal is a 2.0
break. Recorded in roadmap V2.0 alongside the other deferred removals.

## Gate integrity

Two defects in the quality gates themselves. These matter more than any single
finding above, because they are why the findings survived:

1. **`audit.sh` lint gate was inert since it was written.** It ran
   `cyrius lint "$f" || fail`, but `cyrius lint` **exits 0 even when it reports
   findings** — so the gate could only fire if cyrlint failed to execute. It
   also covered `src/*.cyr` only, while CI covers src + tests + benches + fuzz.
2. **CI's lint gate grepped `^\s*warn `**, which does not match cyrlint's
   *deferral* lines. 15 untracked deferrals had accumulated unseen.

Both now parse cyrlint's summary counters, gate warnings **and** untracked
deferrals, cover all four globs, and fail loudly if the output shape changes
rather than silently passing. The 15 deferrals were cleared (cross-referenced
to CHANGELOG/roadmap, or `#skip-lint` where the phrase was incidental prose).

This is the same failure mode as the 1.5.2 fmt gate, where a silently
no-op `cyrius fmt` made every file report as drifted. The lesson is now
encoded in both gates: **a broken tool must never read as a clean result.**

## Reviewed and found clean

- **Command injection.** Every subprocess goes through `exec_vec` /
  `exec_capture` with an explicit argv vector and an **absolute** binary path
  (`/usr/bin/udevadm`, `/usr/bin/bootctl`, `/usr/bin/fusermount`, `/usr/bin/dd`,
  `/usr/bin/efibootmgr`, `/usr/bin/journalctl`, `/usr/sbin/ip`,
  `/usr/bin/mkdir`, `/usr/bin/argonaut`). No `sys_system`, no shell, no PATH
  lookup. The 1.5.0 argv-vec migration holds.
- **Fixed buffers.** All 5 `var buf[N]` sites audited for max write index:
  `bootloader tok[128]` (clamped to 127), `error ebuf[24]`/`ibuf[24]`,
  `netns nft_pid_buf[24]`, `update bc_buf[24]`. All in bounds. None returns a
  borrowed pointer to static per-fn storage, so the cyrius static-data
  clobber hazard does not apply.
- **Other heap read loops.** `update.cyr` (three sites) and
  `agnodrm_read_fd_to_str` all reserve the terminator byte correctly; `fuse`
  was the only outlier (F-5).
- **`break` in `var`-declaring while loops.** CLAUDE.md forbids this. A
  brace-matching analyser found 10 such loops. Tested empirically against
  cyrius 6.5.35: the break form and the prescribed flag+continue form produce
  identical results. The rule appears **stale** for this toolchain — the 10
  sites are correct. Left unchanged rather than churning working parsers; see
  *Follow-ups*.
- **Path traversal.** No module builds a filesystem path from external input.
  Paths are compile-time literals (`/proc/mounts`, `/dev/dri`, `/boot/...`) or
  device names read back from the kernel.
- **`netns` IP/CIDR scratch buffers.** `host_ip`/`agent_ip` `alloc(16)` hold at
  most `"10.100.254.1"` + NUL = 13. `tbuf alloc(4)` holds `h % 255` ≤ 3
  digits. In bounds.

## CVE landscape

Interfaces bound by the surviving modules, reviewed for currently-relevant
classes:

| Interface | Module | Exposure |
|---|---|---|
| DRM/KMS ioctl | drm | `DRM_IOCTL_VERSION` two-call length pattern (F-4), `DRM_IOCTL_GET_CAP`. Read-only queries; no mode-setting, no dumb-buffer allocation, no PRIME fd import — the historical DRM CVE surface (use-after-free in buffer handles, GEM refcount bugs) is not reachable from this API. |
| udev / udevadm | udev | Subprocess, parses `--export-db` text. No netlink uevent socket, so the uevent-spoofing class does not apply. |
| /proc/mounts | fuse | Text parse; octal-escape unescape hardened at 1.1.14 (F-7). F-5 here. |
| FUSE mount/unmount | fuse | Delegates to `fusermount` with argv. No direct `/dev/fuse` protocol handling, so the FUSE notify-reply and splice CVE classes are out of scope. |
| systemd-journal socket | journald | `AF_UNIX` `SOCK_DGRAM` send. Unauthenticated by design (any process may write to the journal socket) — documented in SECURITY-NOTES, not a defect. |
| netns / nftables | netns | `ip` + nft ruleset generation. F-6/F-7 here. Ruleset is generated, never parsed from untrusted input. |
| bootloader (/boot) | bootloader | Read-only config parse + cmdline validation. F-1/F-2 here. |
| A/B update | update | Local file paths only; **manifest `sha256_digest` is parsed but never verified** — structural validation only. Tracked at roadmap V1.5.x, blocked on a stdlib SHA-256. Do not treat `update_verify_manifest` as an authenticity check. |

## Follow-ups

- ~~**Confirm or retire the `break`-in-`var`-loop rule.**~~ **Resolved
  2026-08-24 (post-release): rule retired.** Re-tested well past the single
  case reported above — a 10-shape harness covering the nested inner-loop
  form, vars declared after the break, loop vars read after a break exit, and
  sequential breaking loops, run on **x86_64 and aarch64** (the latter under
  `qemu-aarch64`, the arch that carried the historical sub-8-byte struct-load
  bug). All identical between the two forms. A `defer` registered before the
  loop still runs on the break path — the plausible original motive, and the
  gap in the first test. The 111-assertion suite and all 3 fuzz harnesses also
  pass under `qemu-aarch64`, exercising every one of the 10 sites. Origin
  research: the rule entered as general house guidance in the 1.0.1 CLAUDE.md
  restructure (`562a014`); no audit finding, issue, or ADR ever recorded a
  reproducer. Removed from CLAUDE.md § Rules, with the verified behaviour
  recorded under Cyrius Conventions in its place. The 10 sites are unchanged.
- **Allowlist-based cmdline validation** (roadmap V2.0) — the structural
  answer to F-1.
- **`/proc/mounts` truncation should surface** rather than silently returning a
  partial list.
- **Remove `bootloader_is_dangerous_token`** at 2.0 (F-2).
