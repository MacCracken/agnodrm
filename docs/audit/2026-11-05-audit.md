## F-1 (MEDIUM) — predictable temp file is followed through a symlink

The same class as cyrius's **CYRIUS-2026-0034**, fixed in `lib/io.cyr`'s `file_write_atomic`.
agnodrm does not call that fn, so the bump inherits nothing here.

| Site | Temp path | Open flags |
|---|---|---|
| `update_atomic_write` (`src/update.cyr:75`) | `<path>.tmp` | `O_WRONLY \| O_CREAT \| O_TRUNC` |
| `update_atomic_copy` (`src/update.cyr:143`) | `<dst>.tmp` | `O_WRONLY \| O_CREAT \| O_TRUNC` |
| `netns_apply_nftables_ruleset` (`src/netns.cyr:607`) | `/run/agnos/nft-tmp-<pid>.conf` | `O_WRONLY \| O_CREAT \| O_TRUNC` |

None passes `O_EXCL` or `O_NOFOLLOW`, so `open` follows a symlink already at the temp path.

**Reproduced** on x86_64 against the 1.6.3 sources, for both `update_*` fns. With no symlink
planted, a control run left two victim files untouched. With `<path>.tmp` planted as a symlink:

- Both calls returned `Ok`.
- Each victim file held the attacker-chosen target of the write: `update_atomic_write`'s data and
  `update_atomic_copy`'s source bytes.
- Each destination was left as a **symlink to the victim**, because the rename moves the symlink
  over `<path>`. Later reads and writes of the destination follow it too.

The netns site was read, not run: it needs privileges to reach `ip netns exec`, and the `open` has
the same shape.

**Preconditions.** The attacker must be able to create an entry in the destination's directory, or
in `/run/agnos`, and the caller must write with more privilege than the attacker has. The severity
is MEDIUM for that reason. The write lands with the caller's privileges and the file keeps the
victim's existing mode.

**Exposure today.** Inside agnodrm, `update_save_state` and `update_switch_slot` reach `update_atomic_write`. stiva, the one
workspace consumer, calls none of the three. `update_atomic_write` and `update_atomic_copy` take a
caller-supplied path, so exposure depends on each caller's directory. Whether `/var/lib/agnos` and
`/run/agnos` are root-only on an AGNOS image was not checked.

**Suggested fix.** Create the temp with `O_EXCL | O_NOFOLLOW`; the stdlib names both per target, so
no raw flag literal is needed. Points to settle:

- `<path>.tmp` is a fixed name, so with `O_EXCL` a temp left by a crash blocks every later write. It
  needs a retry over unique names, as upstream's `_io_tmp_open` does (a taken name is skipped, up to
  64, then refused), or an explicit stale-temp policy.
- Calling `file_write_atomic` would need the consumer floor at the first toolchain carrying
  CYRIUS-2026-0034 (6.6.20; the floor is 6.6.6), and its fsync and rename behaviour would
  need checking on agnos.
- Add a regression test that plants the symlink and asserts the victim is unchanged.

### F-1 resolution (1.7.0)

All three sites now go through `agnodrm_tmp_create`, which creates `<base>.tmp.<pid>.<ctr>` with the
stdlib's `file_create_exclusive`. It refuses a name that exists as anything, including a dangling link;
a taken name moves to the next counter, and after 64 the call returns `-EEXIST` having written nothing.
`file_create_exclusive` is in the stdlib at the 6.6.6 floor, so the fix does not raise it.
`file_write_atomic` was not used: it ignores `xfsync`'s result, and agnodrm fails on a failed fsync.

Verified:

- `test_tmp_exclusive`: 96 assertions, on x86_64, under `qemu-aarch64`, and on cyrius 6.6.5, 6.6.6 and
  6.6.20. Restoring `O_TRUNC` fails 9 of them; removing the retry, retrying on every error, not advancing
  the counter, not seeding it and removing the null guards each fail the suite.
- `netns_apply_nftables_ruleset`, which this report could only read, was attacked live in a user
  namespace with a private tmpfs on `/run`. On tag 1.6.3 the victim was overwritten with the ruleset. On
  1.7.0 it was untouched, the planted link was left alone, and the real temp was removed.

Two things the first cut got wrong, found by the closeout review and fixed before release:

- **The counter restarted at 0.** A process with a fixed pid (PID 1, a container) walked the same 64 names
  after each crash, so 64 crashes refused every later write. It now starts from `getrandom`, with
  `GRND_INSECURE` so that early boot never blocks. As real PID 1 in a pid namespace, each run leaving its
  temp behind, an unseeded build refused from run 65; the seeded build created 100 of 100.
- `agnodrm_tmp_create` had no null guards. It now returns `-EINVAL` before creating anything.

Residual, accepted and documented in `docs/SECURITY-NOTES.md`:

- **Name length.** The suffix is up to about 23 bytes, so a target file name over about 232 bytes fails with
  `ENAMETOOLONG`. The old `.tmp` suffix allowed 251.
- **Stale temps.** A crash leaves a temp behind, and nothing cleans it up.
- **The `nft` swap window.** The temp is closed before `nft -f` reads it, so whoever can write to
  `/run/agnos` could swap it in that window. `/run/agnos` must stay root-only. The same access could already
  replace `<path>` for the `update_*` fns, so this is not new access there.

## F-2 (LOW) — capture reads empty when the parent started with std fds closed

Inherited from `lib/process.cyr`, with no fork of agnodrm's own involved. At the 6.6.20 pin the
stdlib's child redirect runs `sys_dup2(fd, N); sys_close(fd)` with no same-fd guard. If the parent
started with fds 0 and 1 closed, the pipe lands on those fds and the child closes its own stdout.
Fixed upstream at **6.7.15** (`2026-10-18-process-capture-redirect-closes-its-own-std-fd.md`).

**Reproduced** on x86_64 with `agnodrm_run_capture` running `/bin/echo hi`: 3 bytes with normal fds,
and `Ok` with 0 bytes when started as `./cap <&- >&-`.

No boundary is crossed: the parent's own fd state drives it. The effect is an empty result reported
as success, which `bootloader_list_boot_entries` would read as bootctl printing nothing and fall
through to reading `loader/entries`. No agnodrm change is needed; the fix arrives with a pin at
≥ 6.7.15.

## Reviewed and found clean

- No `sys_system()` in `src/`, and no raw `syscall(N, …)` (unchanged from 1.6.2).

### F-3 (HIGH) — `update_rollback` undoes its own switch

`src/update.cyr` `update_rollback` loads `state`, calls `update_switch_slot`, which persists the previous
slot and `boot_count = 0`, then saves its own stale `state` over that.

Reproduced from slot B, `boot_count` 3: the `next-slot` marker read `a`, and the state file still held
`"current_slot":2,"boot_count":3`.

On a host with no `agnos.slot=` on the kernel cmdline, `update_get_current_slot` falls back to that file, so
the next `update_apply` targets the slot the host is **running from**. The review reproduced that end to end
with file-backed slots: `rootfs_a` was overwritten. With `agnos.slot=` on the cmdline only the persisted state
is wrong, which is MEDIUM.

### F-4 (MEDIUM) — `update_apply` guesses the live slot

With `agnos.slot=x` on the cmdline, `update_get_current_slot` returns `Err`, `current` keeps its `SLOT_A`
default, and `dd` wrote slot B. A wrong guess overwrites the running root, so this should fail closed.

### F-5 (MEDIUM) — dropped `update_save_state` results

At `update_apply`, `update_switch_slot` and `update_rollback`. Reproduced: with the state directory missing,
`update_switch_slot` returned `Ok` and nothing was persisted. `agnodrm_tmp_create`'s `-EEXIST` is one more way
to reach this silent path.

### F-6 (MEDIUM) — bootctl continuations hide `options` from the validator

A continuation whose first word ends in `:` reads as a label, and a whitespace-only continuation ends the
block. Reproduced by feeding the parser text directly, not through a real `bootctl`: `options: root=/dev/sda`,
then `x: init=/bin/sh`, parsed as `root=/dev/sda`, and `bootloader_validate_kernel_cmdline` returned `Ok`. A
continuation of `id: b.conf init=/bin/sh` replaced the entry id. A real label's colon sits in a fixed column,
which would separate the two.

### The rest

- **F-7:** 227 mounts in 36 KiB gave `Ok(61)` from `fuse_parse_proc_mounts`. A FUSE mount past the cut would
  read as not mounted; this was tested with tmpfs, not a real FUSE mount.
- **F-11:** seen directly: with `udevadm` missing, `udev_list_devices` returned `Ok(0)`, although it documents
  `Err` on exec failure. A fix needs `exec_capture_status`, so the floor at ≥ 6.6.7.
- **F-14:** found by the closeout's cleanup sweep. Changing it is a behaviour change: `journalctl -t agnosys`

Also recorded by the review: the stale-comment item at `src/bootloader.cyr` was corrected in 1.7.0, and
`file_create_exclusive` is a non-atomic pre-check on agnos below cyrius 6.6.9, which `agnodrm_tmp_create`'s
comment now says. agnodrm's own callers return `not_supported` on agnos before reaching it.

### The first cut of these repairs was wrong

The test suite passed at every stage below. An independent review of the repair diff found three **HIGH**
regressions before release, each reproduced:

1. **The F-3 fix moved the danger instead of closing it.** With the state now correct, a rollback followed by
   `update_apply` before the reboot targeted B, the slot the host was still running from. A test asserted this
   as right. The state file records where the next boot goes, and has no way to say where this one came from.
   So `update_apply` no longer reads it: that is the F-4 row above, and it also covers a firmware fallback.
2. **The F-11 fix defeated the bootctl truncation guard.** A reader that stops at a full buffer closes the
   pipe, so the tool dies of SIGPIPE. Reading that as a tool failure skipped the size check, and the fallback
   returned Ok with every UKI missing from what the cmdline validator saw. It failed open.
3. **The F-11 fix broke `journald_query` for ordinary queries:** `--lines 50` and up returned `Err` on this
   host, by the same SIGPIPE path.

The same review found MEDIUM and LOW defects in the repairs, also fixed: `udev_list_devices` lost its graceful
truncation; a failed switch erased an earlier switch's marker; a stale BootNext could outlive a rollback; a field
name holding `=` reopened the F-9 forgery. A second pass over those fixes found three LOW items, also fixed: a
zero-length buffer hid tool failure; `_update_cmdline_slot` read tokens inside quotes and past `--`, so stray text
could still overwrite the live slot; and the field-name check had no test.

### Residual, accepted

- **`update_apply` needs `agnos.slot=` on the kernel cmdline.** Nothing in the workspace emits it yet, so a host
  whose boot entries lack it refuses every update. No workspace code calls `update_apply` today.
- `update_get_current_slot` keeps its state-file fallback and its slot A default, documented as a guess for
  display. `update_apply` does not use it.
- With `agnos.slot=` set, a rollback then `update_apply` before the reboot writes the other slot, which is the one
  about to boot. The running slot is safe; the rollback image is not.
- With `--grep`, exit 1 cannot tell no match from a bad regex, so a bad regex reads as no entries.
- Restoring the marker after a failed save, and clearing BootNext, are best effort. A failed restore needs the
  disk to fill between two writes to one directory, and could not be reproduced.
- The netns temp is still closed before `nft -f` reads it; see F-1.

### Test seams

`_update_root`, `_netns_ip_path`, `_bootloader_bootctl` and `_journald_tool` are private globals, 0 outside
`tests/tcyr`. They retarget fixed host paths and tools so a test never runs a host's `efibootmgr`, `argonaut`,
`bootctl`, `ip` or `journalctl`.

### Repairs reviewed

Independent review ran over the repairs themselves, five rounds on the update flows, because the first repair of this
state machine was wrong. It held **3 HIGH** regressions with all 1,413 tests green, which is the second release running
that a green suite has hidden HIGH defects in a repair (see 1.7.1 below).

- **A rollback wrote its state first.** A power cut there booted the bad slot with the record gone. Moving back now
  writes the marker, the firmware, then the state; see
  [`001-slot-write-order.md`](../architecture/001-slot-write-order.md).
- **Confirming promoted any pending image**, including one nothing had switched to.
- **The hold before `dd` was not proven:** a failed `efibootmgr`, a stale BootNext and an unreadable marker each let it
  pass.

Later rounds found smaller things, and a HIGH and a MEDIUM that came from exempting a failing `efibootmgr`. "The cmdline names
the target" and "a boot has been counted" both looked like proof that a BootNext was spent, and neither is: a switch made
this boot leaves it armed. After two failures the exemption was removed rather than repaired a third time: on an EFI host
a failing `efibootmgr` refuses a rollback or an update until it works. The core review's second round found only LOW
items, and gate 14's flaw before that: it could not fail, since earlier gates re-vendor `lib/`.

The last round simulated a power cut at every write of the three flows, with and without a BootNext outstanding and with
`efibootmgr` failing: 56 rows, none bad. That is a model of the boot order in a scratch harness, not a real power cut.

### Residual, accepted

- **The manifest is not signed.** `verify` catches a corrupt image, not a forged one. Authenticating updates belongs with
  sigil, and is roadmap work.
- **On an EFI host with a failing `efibootmgr`, a rollback and an update refuse until it works.** This trades availability
  on a host already broken for a rule that cannot be wrong. The marker has moved and the record stays, so a retry finishes.
- **A state file written by 1.7.1's `update_apply`** has `rollback_available` set with nothing switched, and reads as a
  trial. Nothing in the workspace has ever run that code, so no schema field was added for it.
- **A value holding a blank line** can still start a block of its own in `--export-db`. No parser of this format can tell
  it from a device, so a listing is what `udevadm` printed, not proof a device exists.
- **`udev_validate_rule` and the cmdline validator are denylists.** `ATTR{...}` writes pass the first. `efi`, `uki`,
  `uki-url` and `extra` keys are not read from BLS entries, so such an entry shows no `linux`.
- **Inert fields:** `enable_nat`, the netns DNS fields, `min_version`, `max_retries` and `backup_dir`.
- **A message over about 212 KB** returns `EMSGSIZE`. The sealed-memfd path is not implemented.
- **With `--grep`, exit 1** still cannot tell no match from a bad regex, and a hostile pattern has no deadline.
- **`netns_generate_agent_ips` keeps no registry**, so two agents can still hash to one subnet.
- **Two mutants survive, by design.** A failed directory fsync after a successful rename cannot be injected here. A temp
  born 0644 rather than the target's mode differs only for the moment before `fchmod`; the helper is tested directly.
- Nothing updates `BootOrder`, so whether a slot stays selected past its one `BootNext` depends on argonaut. Not checked.
